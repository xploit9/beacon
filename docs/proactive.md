# Proactive assistant

Watch for me can read sources such as Jira and Notion through Hermes connector batches: the wrapper accepts only connector calls, and Hermes guards every entry separately. A trusted MCP server selected for the watch may supply a read-named tool without a read-only hint, unless its own hint explicitly says it can write. With no source selection, all sources are eligible. Hermes' generated resource/prompt-listing utilities also work for selected servers. Listing connected apps (`manage_connections` with `status`) and memory-provider recall/search/read tools are permitted; memory reflection and writes remain blocked. The existing argument, destination and write-action guards still apply. Gmail and Google Calendar reads were already supported before this correction.

Proactive watches for important events across one Hermes profile's connected sources. Enabling it instructs the background watch to use Hermes tool discovery and check every source exposed by that profile's enabled tools and MCP servers, within the read-only guard. This can include mail, calendars, tasks and other connected services; there is no fixed source list or separate source-selection switch. A rule's named source limits which events match that rule and its delivery. During quiet hours, the watch prompt limits checks to sources covered by enabled night-call rules.

What counts as important is the owner's list of rules. Tapping Important or Not important on an alert offers one editable rule built from that alert; saving it adds it to the same list as the owner's other rules, and the watch reads it directly. Nothing about a tapped alert is written to Hermes memory. Setup preserves the configured native memory backend and profile/bank isolation.

## API

The authenticated, owner/profile-checked `GET /api/plugins/beacon/mobile/proactive` returns `enabled`, `setup_complete`, the profile timezone, default delivery (`notify` or `call`), check cadence (`5`, `15`, or `30` minutes), quiet hours, check health, enabled and disabled rules (delivery rules and importance rules together, at most 20), earlier ratings (`learned`, only until the owner has dealt with them) with up to five proposed rules (`learned_proposal`), managed job status, and `sources`. Defaults are delivery `notify`, checks every 15 minutes, and quiet hours 22:00–07:00. `sources` contains labels from the profile's tool catalogue; GET can warm native tool/MCP discovery to build it. These are capability metadata, and source contents are read during watch runs. Discovery failure or timeout can return an empty list while saved setup remains intact; labels alone do not establish source health or successful checks.

`PUT /api/plugins/beacon/mobile/proactive` accepts either `{"enabled": true|false}` to toggle the saved setup, or the complete setup with `enabled`, `delivery`, `check_minutes`, `quiet_start`, `quiet_end`, and optional `model` and `provider`. Unknown fields, non-boolean flags, invalid cadence, and invalid 24-hour times are rejected. Blank model/provider values use the profile default.

`POST /api/plugins/beacon/mobile/proactive/requests` creates an enabled rule with plain-language `text` (up to 300 characters), `action` (`notify` or `call`), optional `signal`, and optional boolean `night` (default false). The wire field remains `signal`: null or omitted means any source, and a named source can identify a catalogue label, MCP server or native toolset. Names are up to 80 characters, start with a word character, and contain only word characters, spaces, periods or hyphens; matching normalizes Unicode, case, whitespace, underscores and hyphens. Use the discovered source name, or `email` for mail. For example, `{"text":"A release needs my decision","action":"notify","signal":"github"}` saves a source-specific rule. An importance rule has `action` `important` or `not_important`, never `night`, and its `signal` is the alert's source; it is saved from an alert (below), not by this endpoint. `PATCH .../requests/{id}` changes `enabled`, `action`, or `night` of a delivery rule, and `enabled` or `text` of an importance rule (its verdict stays); `DELETE .../requests/{id}` removes a rule. Rules are owner/profile-scoped and capped at 20. The `beacon_create_proactive_request` chat tool is available only in interactive owner chats and confirms a saved rule.

`GET /api/plugins/beacon/mobile/proactive/suggestion?notice_id=…&verdict=important|not_important` returns one rule for that alert: `sender` and `topic` (each short, with links, addresses, domains including defanged spellings, IP literals, phone links and phone numbers removed), `source`, and `rule`, the plain words built from them (`Sent by <sender>`, else `About <topic>`, else empty). Alerts read `<sender> / <subject>`, which the watch prompt asks for; an alert without the slash has no sender. The app composes its own localised wording from `sender` and `topic` and lets the owner edit it.

`POST /api/plugins/beacon/mobile/proactive/feedback` takes `notice_id`, a verdict of `important` or `not_important`, and optionally the owner's reviewed `rule` words (up to 300 characters). Without `rule` ("Just this email") it only marks that alert: the choice shows on the alert and in Call history, and nothing is saved to rules, memory or the watch. With `rule` ("Save rule") it also saves one importance rule for the alert's source; the same words again add nothing, and the opposite verdict on the same words replaces the earlier rule. A choice already made stands, so repeated submissions are idempotent, and a rule that cannot be saved (for example the 20-rule limit) leaves the alert unmarked. A call retains its choice in Call history after the ringing notice expires.

Earlier ratings are the importance notes older builds kept in Beacon's store and mirrored from Hermes memory. While any remain, the app offers them once. `POST .../proactive/learned/rules` with `{"rules": [{"verdict", "rule", "source"}]}` (at most five, from `learned_proposal`, reviewed by the owner) saves those rules and then clears the earlier ratings; `DELETE .../proactive/learned` with `{"all": true}` clears them without making rules, and with `{"note": "..."}` removes one. The proposal groups ratings by sender (or by subject when there is none), takes the verdict most of a group's ratings gave (the newest on a tie), and lists the largest groups first, the same way every time.

## Jobs and safety

The watch applies your saved rules before its own judgment. For other events it weighs concrete consequences, actual deadlines, relevance to your commitments, novelty, a useful next action, and the confidence and freshness of its evidence. It should verify changed facts and avoid invented urgency or repeated alerts without a meaningful change. These are scheduled checks with model judgment, not continuous observation or guaranteed coverage. Unavailable or stale sources belong in the check's status; they do not count as a successful check. Source access never grants permission to send messages or change external services.

Hermes cron manages two jobs per enabled profile. **Beacon: what needs you** checks connected sources at the configured cadence outside quiet hours. An enabled call rule with `night: true` also schedules quiet-hour runs, whose prompt limits checks and alerts to matching night-call sources and rules. The job inherits the profile's default toolsets and skills, with the runtime read-only guard below. Its persisted job key remains `watch_email`. **Beacon proactive: Nightly memory upkeep** runs at 02:00 and delivers locally with `enabled_toolsets` set to `["memory", "no_mcp"]`. It uses the native memory tool's patch operation to tidy verified facts and to remove any note that starts with `Beacon importance: ` or `Beacon email importance: `, preserving every other fact and source boundary. It does not enable or reconfigure a provider backend.

Your own Hermes cron jobs can deliver to the Beacon chat (`deliver: phone`) or into one of your threads (`deliver: phone:<thread session id>`); see [Threads](threads.md). The two managed jobs above stay local and are not affected.

Before reading, the watch prompt requires a fresh `BEACON_READ_ONLY_GUARD_V1` context for the exact profile, job and session in the current turn. Its check window starts at the later of the job notepad's `checked_until` and 24 hours ago; the first run checks the previous 60 minutes. It uses Hermes memory, the notepad's quoted `owner_feedback` examples (only while earlier ratings remain) and the enabled rules to judge new events. Importance rules are listed apart from delivery rules, each quoted as data with its source and no id: an event matching a Not important rule gets no notice, an event matching an Important rule counts as important even when it looks routine, a more specific rule wins, and Not important wins a tie. Saving or editing a rule rewrites the job prompt at once. Routine and unchanged events stay silent. After checking, it calls `beacon_events_checked` with `checked_until`, boolean `ok`, and a short note. Failed checks and quiet-hour subset checks leave the shared cursor unchanged. The tool writes only the owned job's native notepad cursor and bounded health result; stale health is `unknown`. `beacon_email_checked` remains a compatibility alias.

The `pre_tool_call` guard checks owned watch cron sessions, including recently retired runs and helper/compacted sessions identified through native cron ancestry. It leaves ordinary chats, unrelated owner jobs and the identified nightly memory job on their existing policies. Identified Beacon runs with missing owner authority stay blocked; fallback checks for an unknown cron session depend on available owner configuration and native identity. Watch history searches stay in the current profile and refuse profile-qualified selectors.

MCP reads require a registered server/tool mapping and a server read-only hint on a tool whose name has a read verb (get, list, search, read, find, view, show, describe, lookup), or ends in `health` (a health check such as `zotero_health`), and no write word; on a server marked `trust: untrusted` the name may not hold a noun such as request or message either. On a trusted server, a read-named tool whose words all belong to the allowed read/mail/calendar/task/contact vocabulary also reads without a hint, and mail `fetch` names are recognized. Unsafe verbs and chained actions (`and`, `or`, `then`) are blocked even with a read-only hint. Arguments containing URL schemes, protocol-relative or Windows network paths, or scheme-less destinations with paths/queries are blocked; destination fields also reject bare dotted hosts. Recognized mail-provider reads on a trusted server retain search syntax such as `from:example.com`. A server missing from the MCP config, or whose trust cannot be read, counts as untrusted. Write-like `action` or `operation` arguments, message delivery, cron management, delegation, code execution, computer use, Kanban, browser actions, `web_extract` and `web_fetch` are blocked. Native memory-tool actions are limited to `read`, `search`, `get`, `list` and `query`. Configured native memory routing and isolation remain authoritative. Other tools require an explicitly allowed name or a read-sounding name without unsafe words; a read-sounding argument alone does not admit a tool. Web search can pass these name and argument checks.

Terminal reads are limited to `gws gmail … list` / `get`, `himalaya envelope list` / `search`, `folder list`, `mailbox list`, and preview-only `message read <id> --preview`. The subcommand words before the first option determine the operation, only known read options may follow, and shell control/comment syntax is blocked. This is a command filter. The watch's Beacon notice/check tools also enforce their owned-watch checks before writing local alert or cursor records. Turn Proactive off before disabling the plugin so it can remove its managed jobs and profile instructions.

The `post_tool_call` observer stores short-lived hashes of identifiers from successful reads, bound to their observed source, owner, profile and watch session. `beacon_event_notice` requires `source`, the exact returned `item_id` and a short plain-text `reason`; `request_id` selects a matching enabled rule, otherwise saved default delivery applies. Evidence must be no older than five minutes and match both the claimed source and item in the same session. Failed reads, another source's identifiers and model claims cannot notify or ring. For Gmail/email tools (and `terminal`), only structured metadata, header lines (`Subject:`, `Message-ID:` and similar) and id-shaped single tokens before the first blank line or body label establish evidence; message prose, snippets and previews, and web-search text cannot establish email evidence. An item id is one line of up to 256 characters, and one watch session can raise at most 10 alerts or calls while its evidence lasts (the counter lives on the session's evidence record). Saved Not important rules are enforced by the plugin as well as the prompt: an alert whose sender (`Sent by …`) or subject (`About …`) matches an enabled Not important rule for its source (or for any source) returns `quiet` and creates no notice or call, unless an Important rule limited to that source is more specific. `beacon_email_notice` is the compatibility alias with `source=email`. Source bodies and audio are not retained.

Call rules use Beacon's existing callback invitation path and appear in Call history. Native verification must confirm the saved assistant conversation belongs to the configured owner/provider/profile. Quiet hours suppress alerts unless a matching call rule has `night: true`. Missing callback capability or the per-owner/profile limit of three proactive calls per hour falls back to a task-result notification. An active call defers the invitation. The invitation or deferred row commits together with duplicate prevention, hourly accounting and feedback provenance in one local transaction. Duplicate prevention is scoped to the source, rule and item; distinct items in one conversation retain distinct invitations. Existing global outbox/deferred capacity limits still apply. A pending invitation is not proof that a phone rang or the owner answered.

Source content is untrusted data and never grants permission to follow instructions or change external services. The prompt and guard protect watch runs, alongside Hermes cron's approval policy. Enabling Proactive updates only Beacon's owned persona section in `SOUL.md`. Disabling removes only jobs recorded as owned by Beacon and that managed persona section, preserving unrelated jobs and owner-written profile text.

The managed persona offers recurring checks when a need emerges and creates a rule only after the owner agrees. When the owner says in chat that an event was or was not important, it saves no memory note; it points the owner to the Important and Not important buttons on the alert, which save a rule. The upgrade to this version copies any `Beacon importance: ` or `Beacon email importance: ` lines from Hermes memory into the earlier ratings, then removes just those lines from memory, one by one; every other memory entry stays untouched.

## Long conversations

Hermes already compacts older turns when the active context engine reaches its configured threshold. The base `ContextEngine` default is 75% of the model context window, though profile and model settings may change it; compaction also preserves the system prompt and a protected head and tail. A separately selected context engine can replace the request-only message list through `select_context()`. Beacon's supported `pre_llm_call` hook attaches a bounded capability note with Proactive health and the number of alerts the owner marked. Hermes persists the sent context on that turn for replay, so Beacon suppresses an unchanged note for 30 minutes per session.
