# Proactive assistant

Proactive watches for important events across one Hermes profile's connected sources. Enabling it instructs the background watch to use Hermes tool discovery and check every source exposed by that profile's enabled tools and MCP servers, within the read-only guard. This can include mail, calendars, tasks and other connected services; there is no fixed source list or separate source-selection switch. A rule's named source limits which events match that rule and its delivery. During quiet hours, the watch prompt limits checks to sources covered by enabled night-call rules.

Hermes profile memory holds source-specific importance preferences the owner gives in chat. Important / Not important taps are kept in Beacon's owner/profile store and shown only to the watch through its job notepad. Setup preserves the configured native memory backend and profile/bank isolation.

## API

The authenticated, owner/profile-checked `GET /api/plugins/beacon/mobile/proactive` returns `enabled`, `setup_complete`, the profile timezone, default delivery (`notify` or `call`), check cadence (`5`, `15`, or `30` minutes), quiet hours, check health, enabled and disabled rules, up to 20 learned source notes, managed job status, and `sources`. Defaults are delivery `notify`, checks every 15 minutes, and quiet hours 22:00–07:00. `sources` contains labels from the profile's tool catalogue; GET can warm native tool/MCP discovery to build it. These are capability metadata, and source contents are read during watch runs. Discovery failure or timeout can return an empty list while saved setup remains intact; labels alone do not establish source health or successful checks.

`PUT /api/plugins/beacon/mobile/proactive` accepts either `{"enabled": true|false}` to toggle the saved setup, or the complete setup with `enabled`, `delivery`, `check_minutes`, `quiet_start`, `quiet_end`, and optional `model` and `provider`. Unknown fields, non-boolean flags, invalid cadence, and invalid 24-hour times are rejected. Blank model/provider values use the profile default.

`POST /api/plugins/beacon/mobile/proactive/requests` creates an enabled rule with plain-language `text` (up to 300 characters), `action` (`notify` or `call`), optional `signal`, and optional boolean `night` (default false). The wire field remains `signal`: null or omitted means any source, and a named source can identify a catalogue label, MCP server or native toolset. Names are up to 80 characters, start with a word character, and contain only word characters, spaces, periods or hyphens; matching normalizes Unicode, case, whitespace, underscores and hyphens. Use the discovered source name, or `email` for mail. For example, `{"text":"A release needs my decision","action":"notify","signal":"github"}` saves a source-specific rule. `PATCH .../requests/{id}` changes `enabled`, `action`, or `night`; `DELETE .../requests/{id}` removes a rule. Rules are owner/profile-scoped and capped at 20. The `beacon_create_proactive_request` chat tool is available only in interactive owner chats and confirms a saved rule.

`POST /api/plugins/beacon/mobile/proactive/feedback` accepts a Proactive alert's `notice_id` and a verdict of `important` or `not_important`. It saves the alert's short summary as quoted source data with links, addresses, domains (including defanged spellings), IP literals, phone links and phone numbers removed. Notes use `Beacon importance: <source>: ` in Beacon's owner/profile store; source bodies are not saved. The newest 20 reach only the watch's cron notepad as `owner_feedback`. Notification feedback replaces the opposite note for that summary; call feedback is claimed once and repeated submissions are idempotent. A call retains its feedback association in Call history after the ringing notice expires. Earlier Hermes importance notes are mirrored without deleting the owner's originals. `DELETE /api/plugins/beacon/mobile/proactive/learned` with `{"note": "..."}` removes one learned note.

## Jobs and safety

Hermes cron manages two jobs per enabled profile. **Beacon: what needs you** checks connected sources at the configured cadence outside quiet hours. An enabled call rule with `night: true` also schedules quiet-hour runs, whose prompt limits checks and alerts to matching night-call sources and rules. The job inherits the profile's default toolsets and skills, with the runtime read-only guard below. Its persisted job key remains `watch_email`. **Beacon proactive: Nightly memory upkeep** runs at 02:00 and delivers locally with `enabled_toolsets` set to `["memory", "no_mcp"]`. It uses the native memory tool's patch operation to tidy verified facts and source-specific importance notes, preserving existing facts and source boundaries. It does not enable or reconfigure a provider backend.

Your own Hermes cron jobs can deliver to the Beacon chat (`deliver: phone`) or into one of your threads (`deliver: phone:<thread session id>`); see [Threads](threads.md). The two managed jobs above stay local and are not affected.

Before reading, the watch prompt requires a fresh `BEACON_READ_ONLY_GUARD_V1` context for the exact profile, job and session in the current turn. Its check window starts at the later of the job notepad's `checked_until` and 24 hours ago; the first run checks the previous 60 minutes. It uses Hermes importance preferences, the notepad's quoted `owner_feedback` examples and enabled rules to judge new events. Routine and unchanged events stay silent. After checking, it calls `beacon_events_checked` with `checked_until`, boolean `ok`, and a short note. Failed checks and quiet-hour subset checks leave the shared cursor unchanged. The tool writes only the owned job's native notepad cursor and bounded health result; stale health is `unknown`. `beacon_email_checked` remains a compatibility alias.

The `pre_tool_call` guard checks owned watch cron sessions, including recently retired runs and helper/compacted sessions identified through native cron ancestry. It leaves ordinary chats, unrelated owner jobs and the identified nightly memory job on their existing policies; an uncertain Beacon cron identity fails closed.

MCP reads require a registered server/tool mapping and either a server read-only hint or a read-named tool whose words all belong to the allowed read/mail/calendar/task/contact vocabulary; mail `fetch` names are also recognized. Unsafe verbs and chained actions (`and`, `then`) are blocked even with a read-only hint. Arguments containing URL schemes, protocol-relative or Windows network paths, or scheme-less destinations with paths/queries are blocked; destination fields also reject bare dotted hosts. Recognized mail-provider reads retain search syntax such as `from:example.com`. Write-like `action` or `operation` arguments, message delivery, cron management, delegation, code execution, computer use, Kanban, browser actions, `web_extract` and `web_fetch` are blocked. Native memory-tool actions are limited to `read`, `search`, `get`, `list` and `query`. Configured native memory routing and isolation remain authoritative. Other tools require an explicitly allowed name or a read-sounding name without unsafe words; a read-sounding argument alone does not admit a tool. Web search can pass these name and argument checks.

Terminal reads are limited to `gws gmail … list` / `get`, `himalaya envelope list` / `search`, `folder list`, `mailbox list`, and preview-only `message read <id> --preview`. The subcommand words before the first option determine the operation, only known read options may follow, and shell control/comment syntax is blocked. This is a command filter. The watch's Beacon notice/check tools also enforce their owned-watch checks before writing local alert or cursor records. Turn Proactive off before disabling the plugin so it can remove its managed jobs and profile instructions.

The `post_tool_call` observer stores short-lived hashes of identifiers from successful reads, bound to their observed source, owner, profile and watch session. `beacon_event_notice` requires `source`, the exact returned `item_id` and a short plain-text `reason`; `request_id` selects a matching enabled rule, otherwise saved default delivery applies. Evidence must be no older than five minutes and match both the claimed source and item in the same session. Failed reads, another source's identifiers and model claims cannot notify or ring. For Gmail/email tools, labelled message/thread IDs before body sections and structured metadata establish evidence; email body text and web-search text cannot establish email evidence. `beacon_email_notice` is the compatibility alias with `source=email`. Source bodies and audio are not retained.

Call rules use Beacon's existing callback invitation path and appear in Call history. Native verification must confirm the saved assistant conversation belongs to the configured owner/provider/profile. Quiet hours suppress alerts unless a matching call rule has `night: true`. Missing callback capability or the per-owner/profile limit of three proactive calls per hour falls back to a task-result notification. An active call defers the invitation. The invitation or deferred row commits together with duplicate prevention, hourly accounting and feedback provenance in one local transaction. Duplicate prevention is scoped to the source, rule and item; distinct items in one conversation retain distinct invitations. Existing global outbox/deferred capacity limits still apply. A pending invitation is not proof that a phone rang or the owner answered.

Source content is untrusted data and never grants permission to follow instructions or change external services. The prompt and guard protect watch runs, alongside Hermes cron's approval policy. Enabling Proactive updates only Beacon's owned persona section in `SOUL.md`. Disabling removes only jobs recorded as owned by Beacon and that managed persona section, preserving unrelated jobs and owner-written profile text.

The managed persona offers recurring checks when a need emerges and creates a rule only after the owner agrees. When the owner explains an event's importance in chat, it asks the assistant to save one short source-specific preference using `Beacon importance: <source>: ` in Hermes user memory, under the profile's configured policy. This chat instruction is separate from feedback taps, which stay in Beacon's store and watch notepad. Legacy `Beacon email importance: ` notes remain email-specific.

## Long conversations

Hermes already compacts older turns when the active context engine reaches its configured threshold. The base `ContextEngine` default is 75% of the model context window, though profile and model settings may change it; compaction also preserves the system prompt and a protected head and tail. A separately selected context engine can replace the request-only message list through `select_context()`. Beacon's supported `pre_llm_call` hook attaches a bounded capability note with Proactive health and the number of alerts the owner marked. Hermes persists the sent context on that turn for replay, so Beacon suppresses an unchanged note for 30 minutes per session.
